## Refactoring Specification: Contract Versioning via ContractDetails

### Overview

The mutable financial and temporal fields currently residing on the `Contract` entity are to be extracted into a new `ContractDetails` entity. This reflects the business rule that any change to a contract's value, balance, or validity period must be backed by a formal **Appendix** document, creating an auditable history of contract amendments.

---

### 1. Entity Changes

**Remove from `Contract`:**
- `contractValue`, `contractBalance`, `contractStartDate`, `contractEndDate`, `modifiedAt`, `modifiedByUserId`

**Create `ContractDetails` entity with:**

| New Field Name | Origin | Notes |
|---|---|---|
| `contractValue` | was `contractValue` | — |
| `contractBalance` | was `contractBalance` | — |
| `startDate` | was `contractStartDate` | renamed |
| `endDate` | was `contractEndDate` | renamed |
| `createdAt` | was `modifiedAt` | renamed |
| `createdByUserId` | was `modifiedByUserId` | renamed |
| `appendix` | new | `@OneToOne` to `Appendix`; nullable (null  ONLY on initial contract creation) |

`ContractDetails` has a `@ManyToOne` relationship to `Contract`.

---

### 2. Contract Creation

When a new `Contract` is created, a corresponding `ContractDetails` record is **automatically generated** using the values provided in the existing creation DTO (no DTO changes). `appendix` is set to `null`. `createdAt` is set to the current timestamp.

---

### 3. Contract Update

The **update DTO** is modified to include:
```java
private Integer appendixId; // required
```

On update, a **new `ContractDetails` record is created** — the existing ones are never mutated. The new record is populated with:
- `startDate`, `contractValue`, `contractBalance` from the DTO
- `endDate` from the DTO; if `null`, it is defaulted to the `endDate` of the current **PRESENT_VALID** `ContractDetails`
- if 'contractValue' or 'contractBalance' are `null`, they are defaulted to the corresponding values from the current **PRESENT_VALID** `ContractDetails`
- `createdAt` = `LocalDateTime.now()`
- `createdByUserId` from request
- `appendix` resolved and **validated** from `appendixId` — throws if not found

---

### 4. PRESENT_VALID ContractDetails Resolution

Given a contract's list of `ContractDetails`:
- **Single record** → that record is the valid one
- **Multiple records** → filter to those whose `startDate ≤ today ≤ endDate`, then select the one with the **latest `createdAt`**

This logic is encapsulated in a reusable private method in the service.

---

### 5. Response DTO Mapping

`ContractResponseDTO` fields:
```java
private BigDecimal contractValue;
private BigDecimal contractBalance;
private LocalDate contractStartDate;
private LocalDate contractEndDate;
private LocalDateTime modifiedAt;
private Integer modifiedByUserId;
```
contractValue, contractBalance, modifiedAt, modifiedByUserId are now read from the `ContractDetails` record.
startDate and endDate are THE OLDEST value of startDate and endDate from all `ContractDetails` records.

---

### 6. Deliverables

- `ContractDetails` entity + repository
- Flyway migration: drops columns from `contract`, creates `contract_details` table
- Updated `Contract` entity
- Updated service: creation flow, update flow, PRESENT_VALID resolution
- Updated mapper: reads from PRESENT_VALID `ContractDetails`
- Updated update DTO: adds `appendixId`
